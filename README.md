# Geospatial File Measurement API

## Overview

This SDE internship assignment accepts KML files and ZIP files containing one Shapefile. It extracts features, calculates polygon areas and line lengths, and stores the results in SQLite.

Polygon areas are returned in square meters and LineString lengths in meters. Points do not need a measurement. Other geometry types are preserved with an `UNSUPPORTED` status.

## Features

- Validate KML and zipped Shapefile uploads.
- Extract source IDs, geometry types, geometries, properties, and CRS.
- Measure a projected geometry copy while keeping the original coordinates.
- Retrieve file metadata and stored measurements through GET endpoints.
- Return clear errors for invalid files and unknown IDs.

## Tech Stack

Python 3.12, FastAPI, GeoPandas, Shapely, PyProj, SQLAlchemy, SQLite, and Pytest.

Pyogrio is the geospatial reading backend. Uvicorn runs the app, python-multipart handles uploads, and HTTPX is used by FastAPI's TestClient. Direct dependencies are pinned in `requirements.txt` to the versions used for final testing.

## API Endpoints

File IDs are integers generated by SQLite. Upload timestamps use UTC. The responses below are illustrative.

### POST /api/files/

Send a file using the multipart field `file`:

```bash
curl -X POST http://127.0.0.1:8000/api/files/ \
  -F "file=@survey.kml"

curl -X POST http://127.0.0.1:8000/api/files/ \
  -F "file=@survey.zip"
```

Success returns HTTP **201** with file metadata:

```json
{
  "id": 1,
  "filename": "survey.zip",
  "feature_count": 1,
  "crs": "EPSG:32631",
  "status": "COMPLETED",
  "uploaded_at": "2026-10-06T18:00:00Z"
}
```

The original file is saved as `uploads/{id}.kml` or `uploads/{id}.zip`. ZIP extraction is temporary. The database field `source_crs` is exposed as `crs` in API responses.

### GET /api/files/{id}/

Returns file metadata without feature geometries:

```bash
curl http://127.0.0.1:8000/api/files/1/
```

HTTP **200** returns the same metadata fields shown in the POST example.

### GET /api/files/{id}/measurements/

Returns all stored features for the requested file:

```bash
curl http://127.0.0.1:8000/api/files/1/measurements/
```

```json
{
  "file_id": 1,
  "feature_count": 1,
  "features": [
    {
      "id": 1,
      "feature_id": "0",
      "geometry_type": "Polygon",
      "geometry": {
        "type": "Polygon",
        "coordinates": [
          [[500000, 0], [500100, 0], [500100, 100],
           [500000, 100], [500000, 0]]
        ]
      },
      "crs": "EPSG:32631",
      "properties": {"name": "Plot A"},
      "area_m2": 10000.0,
      "length_m": null,
      "measurement_status": "SUCCESS"
    }
  ]
}
```

`id` is the unique database feature ID. `feature_id` is the source ID/index stored as text and may repeat across layers. Geometry and CRS describe the original data. GET requests read stored measurements without recalculating them.

## File Processing Flow

```text
Upload
  → validate extension, size, and ZIP components
  → read with GeoPandas
  → extract features and properties
  → inspect CRS
  → create a projected measurement copy
  → calculate measurements
  → store original geometry and measurements
  → return API responses
```

File and feature rows are saved in one transaction. Failed uploads roll back database changes and remove the saved upload. GET requests read SQLite records.

## CRS Handling

Latitude and longitude are in degrees, so the app never uses them directly for area or length.

- Geographic CRS: estimate a local UTM CRS with GeoPandas `estimate_utm_crs()` using the valid polygons and lines.
- Projected metric CRS: reuse it if both horizontal axes use meters.
- Projected non-meter CRS, such as feet: transform a copy to an estimated local UTM CRS.
- Missing or unusable CRS: return a clear processing error without guessing the source CRS.

GeoPandas `to_crs()` returns a separate measurement copy. Original geometries and source CRS remain unchanged. Points and unsupported geometries need no projected copy because they are not measured.

One measurement CRS is used per dataset. Local UTM suits small regional datasets; large datasets spanning multiple zones can suffer distortion. Polar regions may have no suitable UTM CRS. Dateline-crossing geometries require handling that is not implemented here. Reusing a projected CRS also retains that projection's distortion.

Calculations use the horizontal geometry. Elevation coordinates are preserved but are not included in 3D areas or lengths.

References: [GeoPandas UTM estimation](https://geopandas.org/en/stable/docs/reference/api/geopandas.GeoDataFrame.estimate_utm_crs.html) and [transformation limitations](https://geopandas.org/en/stable/docs/reference/api/geopandas.GeoDataFrame.to_crs.html).

## Measurements

| Geometry | Area | Length | Status |
|---|---|---|---|
| Polygon | Square meters | null | `SUCCESS` |
| LineString | null | Meters | `SUCCESS` |
| Point | null | null | `NOT_REQUIRED` |
| Other types or missing geometry | null | null | `UNSUPPORTED` |
| Invalid/empty Polygon or LineString | null | null | `INVALID_GEOMETRY` |

MultiPolygon, MultiLineString, MultiPoint, and GeometryCollection are currently unsupported for measurement. They are preserved while other features continue processing. Invalid polygons and lines are not automatically repaired.

## Validation and Error Handling

- Unsupported extensions and empty files are rejected; extension checks ignore case.
- Upload limit: **20 MiB** (20 × 1024 × 1024 bytes).
- ZIP archives must be readable and pass checksum checks.
- A ZIP must contain exactly one `.shp` with matching `.shx`, `.dbf`, and `.prj` files in the same archive directory. Optional `.cpg` files provide attribute encoding.
- Traversal, absolute paths, Windows separators/drive syntax, symbolic links, and duplicate ZIP paths are rejected.
- Total declared ZIP contents must not exceed **100 MiB**.
- Validated components are copied to fixed filenames in a temporary directory instead of extracting arbitrary paths.
- Missing/unusable CRS is rejected. Layers must share one source CRS.
- Invalid geometry receives a feature status instead of being silently measured.

| Situation | HTTP status |
|---|---|
| Successful upload | 201 |
| Invalid extension, empty/corrupt file, components, or input-related processing/CRS error | 400 |
| Unknown numeric file ID | 404 |
| Oversized upload | 413 |
| Missing multipart field or non-integer path ID | 422 |
| Upload database/filesystem failure | 500 |

Errors use FastAPI's normal `detail` response, for example:

```json
{"detail": "File not found."}
```

## Design Decisions

- **FastAPI** provides uploads, validation, and API documentation with little setup.
- **SQLite** makes the assignment easy to run without a separate server. This setup is intended for small datasets, not heavy concurrent writes.
- **GeoPandas** reads datasets and transforms coordinates without separate hand-written format parsers.
- **The small architecture** keeps routes, database setup, models, and geospatial logic easy to follow. There are no service or repository layers.
- **Measurements are stored during upload** so GET requests return existing results without repeating the processing work.

## Testing

After activating the virtual environment:

```bash
pytest -q
```

Tests cover uploads, ZIP validation, rollback, geographic/projected CRS, meter and feet units, original geometry preservation, measurement statuses, and GET responses without recalculation. They use temporary databases and files rather than the application database.

The current dependencies emit a `StarletteDeprecationWarning` about TestClient's HTTPX backend through `fastapi.testclient`. It does not fail the tests.

## Docker

Build and run from the repository root:

```bash
docker build -t geospatial-api .
docker run --rm --name geospatial-api -p 8000:8000 geospatial-api
```

In another terminal:

```bash
curl http://127.0.0.1:8000/health
```

The upload and GET examples work against the container too. Stop it with `docker stop geospatial-api`.

The image uses Python 3.12 slim and binary wheels. [Pyogrio wheels include GDAL](https://pyogrio.readthedocs.io/en/latest/install.html), so no separate system GDAL package or compiler toolchain is installed. KML and Shapefile drivers must be available in the installed Pyogrio wheel.

SQLite and uploads live inside the container for this simple run command. Because it uses `--rm`, removing the container deletes that data. Persistent container storage is not configured.

## Learning

This project helped me understand why a Shapefile needs several matching files and how KML can contain multiple layers. I also learned the difference between assigning a CRS and transforming coordinates, and why latitude/longitude measurements cannot be reported directly as meters.

The upload checks gave me practice with ZIP validation, temporary files, and database rollback. Writing the tests helped me separate API behavior from geospatial calculations and check geographic measurements with reasonable tolerances.
